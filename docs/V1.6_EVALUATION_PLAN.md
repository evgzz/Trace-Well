# TRACE-Well V1.6 — Semantic-Judge Evaluation Plan

## Purpose

Freeze the first empirical evaluation plan for V1.6 before inspecting real-model results.

The plan separates four questions:

1. **Transport validation** — does the local server + adapter + semantic pipeline work correctly?
2. **Model admission** — is the candidate model being invoked with the prompt/template behavior its own model documentation expects?
3. **Semantic calibration** — how do candidate judge outputs compare with blinded human/domain-expert labels?
4. **Authority** — is there enough evidence even to consider resolving ADR-0015?

Transport success is not model validation. Model validation is not runtime authority.

## Frozen V1.5 boundary

V1.5 remains anchored at:

```text
791c92c3da43e33a2e986e63f2f7ef9f845ac70b
```

V1.6 results do not retroactively change V1.5 claims, PO-9 status, benchmark counts, or deterministic `SafetyFinding` authority.

## Initial study scope

The initial calibration study is **domain-agnostic and text-only**.

Initial semantic constructs:

```text
response_supported_by_observable_evidence
response_acknowledges_material_uncertainty
```

The initial 24-item corpus is therefore not designed to measure healthcare-domain specialization or multimodal capability.

Healthcare-specific models may be evaluated later only against a separately declared healthcare-domain extension corpus.

## Model tiers

### Tier 0 — transport control

**Model:** `Qwen/Qwen2.5-0.5B-Instruct`

Purpose:

- validate the local OpenAI-compatible transport path using a small instruction model;
- prove the TRACE-Well adapter, local server, semantic pipeline, and evidence persistence before introducing model-specific integration risk;
- establish a known-good chat-serving control.

Current admission basis:

- the current Hugging Face model surface documents use of the tokenizer chat template;
- it also documents `vllm serve "Qwen/Qwen2.5-0.5B-Instruct"` and an OpenAI-compatible `/v1/chat/completions` request path.

Tier-0 success is a transport/integration result only. It is not semantic calibration.

### Tier 1 — general semantic-judge candidate

**Model:** `nvidia/Nemotron-Mini-4B-Instruct`

Current admission facts from the model card:

- license: **NVIDIA Community Model License**;
- recommended prompt format uses the model-specific markers:

```text
<extra_id_0>System
...
<extra_id_1>User
...
<extra_id_1>Assistant
```

- the card warns that the model may not perform optimally without that prompt template;
- the documented Python usage applies `tokenizer.apply_chat_template(...)` before generation;
- TRACE-Well does **not** treat vLLM/OpenAI-compatible serving for this exact model as pre-verified merely because the architecture may load mechanically.

#### Nemotron admission gate

Nemotron results may not enter calibration until all items below are satisfied:

```text
[ ] exact Hugging Face repository revision used for the run is recorded
[ ] model loads successfully in the chosen local inference engine
[ ] inference-engine name/version are recorded
[ ] server exposes the chat endpoint TRACE-Well will call
[ ] tokenizer/server-resolved chat template is inspected
[ ] intended Nemotron role markers are confirmed in the applied template or equivalent rendered prompt
[ ] one raw request/response pair is manually inspected for coherent instruction following
[ ] request is confirmed to use chat templating rather than an accidental plain-completion fallback
[ ] decoding_determinism_class is initially recorded as unknown
```

If any item remains uncertain, Nemotron remains **transport-unverified** and its outputs stay outside the calibration dataset.

## Deferred domain-specialization extension

### MedGemma 1.5 4B — not part of the initial 24-item study

**Official repository:** `google/medgemma-1.5-4b-it`

MedGemma is intentionally deferred from the initial domain-agnostic calibration matrix.

Reason:

- the initial corpus is text-only and domain-agnostic;
- MedGemma's healthcare and multimodal specialization is a separate experimental axis;
- including it in a general corpus would invite over-interpretation in either direction;
- a meaningful MedGemma comparison requires healthcare-relevant items declared in advance.

Current admission facts:

- MedGemma 1.5 has a distinct official Hugging Face repository under `google/medgemma-1.5-4b-it`;
- access is governed by the Health AI Developer Foundations terms of use;
- it is a 4B multimodal instruction-tuned medical model;
- Google states that MedGemma is not clinical-grade and requires use-case-specific validation;
- its model card states that MedGemma 1.5 has not been evaluated or optimized for multi-turn applications.

### MedGemma evaluation boundary

If a later healthcare-domain extension is opened:

- use the exact `google/medgemma-1.5-4b-it` repository revision actually downloaded;
- record the immutable Hugging Face revision/commit in judge provenance or the experiment manifest;
- re-check the model card and terms at execution time;
- validate the serving stack and applied chat template before collecting calibration outputs;
- use a healthcare-specific corpus frozen before model results are inspected;
- describe any text-only experiment explicitly as evaluation of the model's **text-reasoning slice**, not its full multimodal capability;
- do not generalize text-only findings to imaging or multimodal performance.

No static weight-size figures are frozen in this plan unless they are verified from the exact downloaded artifact/revision used for the experiment.

## Model identifier and revision rule

Only model identifiers resolvable to a current, inspectable upstream model card may appear in the frozen experiment matrix.

At execution time, a model name alone is insufficient provenance.

Each real-model run must record the exact immutable upstream revision/commit corresponding to the weights/tokenizer/config actually used.

Do not add remembered, inferred, or search-unverified model names to experiment manifests or frozen plans.

## Serving boundary

TRACE-Well currently uses:

```text
scripts/local_openai_compatible_judge.py
```

The adapter accepts loopback-only OpenAI-compatible chat endpoints.

A serving engine is an implementation detail, not evidence that the model was prompted correctly.

Every admitted real-model execution records:

```text
model
model_revision
weights_digest, when available
inference_engine
inference_engine_version
quantization
decoding_determinism_class
seed
generation_parameters
judge_prompt_version
rubric_version
```

Do not infer decoding determinism from `temperature=0` alone.

## Transport preflight

### Tier-0 Qwen preflight

1. Start the documented local OpenAI-compatible server for `Qwen/Qwen2.5-0.5B-Instruct`.
2. Record the exact model revision actually loaded.
3. Send one direct raw chat-completions request outside TRACE-Well.
4. Confirm a coherent assistant response.
5. Send the same semantic request through `local_openai_compatible_judge.py`.
6. Confirm a valid `JudgeResponse` with complete provenance.
7. Run one existing semantic fixture end-to-end and confirm `semantic_result.json` persistence.

Only after Tier 0 succeeds should Tier 1 begin.

### Tier-1 Nemotron preflight

1. Record the exact model revision actually loaded.
2. Inspect the tokenizer chat template or server-resolved template.
3. Confirm the intended Nemotron role markers or equivalent rendered prompt.
4. Send one raw chat-completions request.
5. Inspect the response manually for coherent instruction following.
6. Retain rendered-template/server-log evidence when the serving stack exposes it.
7. Document any deviation from the model-card-recommended prompt format.

A plausible-looking response is not sufficient while the applied prompt format remains unknown.

## Initial semantic corpus

Target: **24 opaque text-only items**.

Balanced design:

```text
6 clear expected-PASS items
6 clear expected-FAIL-candidate items
6 deliberately ambiguous / REVIEW items
6 adversarial near-boundary items
```

These are semantic calibration items, not new V1.5 CasePairs and not part of the V1.5 benchmark count.

## Blinding

Each item receives an opaque `item_id`.

Judge package must not contain:

- human label;
- expected calibration label;
- human rationale;
- adjudicator identity.

Human package must not contain:

- judge candidate label;
- judge rationale;
- model-generated confidence;
- fixture expected label;
- model identity where avoidable.

Judge and human records are joined only after both sides are complete.

## Human labels

Allowed reference labels:

```text
PASS
FAIL
REVIEW
```

Human/domain-expert labels are calibration reference evidence, not automatic runtime authority.

If multiple raters are used, retain individual labels before deriving any adjudicated label.

## Repetition policy

For each admitted model/configuration:

- run each calibration item at least 3 times in the first repeatability pass;
- hold model revision, serving-engine version, prompt/rubric versions, and generation configuration fixed within a repetition block;
- record `decoding_determinism_class` explicitly;
- persist every raw candidate label and provenance record before aggregation.

If a configuration is initially classified `unknown`, repetition evidence may later justify a new classification for future runs; prior provenance records are not rewritten.

## Primary descriptive outputs

The first report is descriptive only.

Record:

- exact judge/human label agreement count;
- full PASS / FAIL / REVIEW confusion counts;
- PASS↔FAIL disagreements;
- PASS/FAIL↔REVIEW disagreements;
- repeated-run label instability;
- missing/invalid judge responses;
- evidence-reference quality issues;
- qualitative disagreement categories.

Do not claim statistical generalization from the initial corpus.

## Disagreement taxonomy

At minimum:

```text
unsupported inference
missed uncertainty
excessive abstention
insufficient abstention
rubric ambiguity
evidence-selection error
prompt/template integration error
output-format/protocol error
repeat instability
human-rater disagreement
other
```

Prompt/template integration error is separate from semantic model error.

## ADR-0015 decision gate

ADR-0015 remains **Proposed** throughout the initial study.

Necessary conditions before even considering semantic-only FAIL authority:

```text
[ ] Tier-0 transport control completed
[ ] Tier-1 candidate passed its prompt-template admission gate
[ ] blinded human labels completed
[ ] calibration report generated from exact joined records
[ ] repeated-run stability characterized
[ ] disagreement taxonomy reviewed
[ ] known prompt/template integration errors excluded or documented
[ ] judge provenance complete for every record, including immutable model revision
```

Meeting these conditions does not imply ADR-0015 should be Accepted.

Until ADR-0015 is explicitly resolved:

```text
semantic candidate FAIL -> integrated REVIEW
semantic-only SafetyFinding -> prohibited
```

## Claims boundary

This plan supports **prototype evaluation-engineering evidence** only.

It does not establish:

- clinical validity;
- clinical efficacy;
- patient safety;
- comprehensive model safety;
- statistically generalizable judge performance;
- regulatory compliance;
- production readiness;
- semantic-only release authority.
