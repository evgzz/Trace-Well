# TRACE-Well V1.6 — Semantic-Judge Evaluation Plan

## Purpose

Freeze the first empirical evaluation plan for V1.6 before inspecting real-model results.

The plan separates four questions:

1. **Transport validation** — does the selected hosted or local serving path + adapter + semantic pipeline work correctly?
2. **Model admission** — is the candidate model invoked with the prompt/template behavior its own documentation expects?
3. **Semantic calibration** — how do candidate judge outputs compare with blinded human/domain-expert labels?
4. **Authority** — is there enough evidence to justify a separately preregistered validation phase under [`ADR-0015`](adr/0015-semantic-fail-propagation-vs-review.md)?

Transport success is not model validation. Model validation is not runtime authority.

## Frozen V1.5 boundary

V1.5 remains anchored at:

```text
791c92c3da43e33a2e986e63f2f7ef9f845ac70b
```

V1.6 results do not retroactively change V1.5 claims, PO-9 status, benchmark counts, or deterministic `SafetyFinding` authority.

## Initial study scope

The initial calibration study is **domain-agnostic and text-only**.

Initial semantic constructs:

```text
response_supported_by_observable_evidence
response_acknowledges_material_uncertainty
```

Target corpus: **24 opaque items**:

```text
6 clear expected-PASS items
6 clear expected-FAIL-candidate items
6 deliberately ambiguous / REVIEW items
6 adversarial near-boundary items
```

These are semantic-calibration items, not new V1.5 CasePairs and not part of the frozen V1.5 benchmark count.

Healthcare-specific models belong to a separately declared healthcare-domain extension corpus.

## Tier-0 execution paths

Tier 0 supports two distinct execution paths with different evidence ceilings.

### Path A — dedicated Hugging Face Inference Endpoint

Preferred when the goal is **no self-hosting**.

Use a dedicated Hugging Face Inference Endpoint for the exact Hub model and record the immutable deployed revision from endpoint metadata.

Expected advantages:

- no local GPU/server administration;
- direct deployment from the Hugging Face Hub;
- selectable managed serving engine depending on model/endpoint configuration;
- OpenAI Chat Completions compatibility on supported endpoint engines;
- model revision can be pinned in the managed deployment.

Evidence ceiling:

```text
transport_only by default
```

A dedicated-endpoint run may be promoted to `calibration_candidate` only if the deployment exposes enough exact runtime/template/artifact provenance to satisfy the frozen real-model manifest and admission rules.

Unavailable hosted provenance must remain unavailable. Do not fill it with locally inferred or guessed values.

### Path B — local/self-hosted OpenAI-compatible server

Preferred when the goal is **maximum reproducibility/provenance control**.

Use vLLM, Transformers Serve, or another admitted local engine and capture exact model revision, engine version, chat template, rendered prompt, and artifact evidence.

Evidence ceiling:

```text
calibration_candidate when all frozen manifest requirements are satisfied
```

## Model tiers

### Tier 0 — transport control

**Model:** `Qwen/Qwen2.5-0.5B-Instruct`

Purpose:

- validate the real-model OpenAI-compatible transport path using a small instruction model;
- prove the adapter, semantic pipeline, and evidence persistence before candidate-model calibration;
- establish a known-good chat-serving control.

Current admission basis:

- the Hugging Face model surface documents tokenizer chat-template usage;
- it documents `vllm serve "Qwen/Qwen2.5-0.5B-Instruct"` and an OpenAI-compatible `/v1/chat/completions` path;
- Hugging Face Inference Endpoints provide a managed path for deploying models from the Hub with OpenAI-compatible chat APIs on supported engines.

Tier-0 success is an integration result only. It is not semantic validation.

### Tier 1 — general semantic-judge candidate

**Model:** `nvidia/Nemotron-Mini-4B-Instruct`

Current admission facts:

- license: **NVIDIA Community Model License**;
- recommended prompt format uses model-specific `<extra_id_...>` role markers;
- the model card warns that performance may degrade without that template;
- documented Python usage applies `tokenizer.apply_chat_template(...)`;
- TRACE-Well does **not** treat any managed/local OpenAI-compatible serving path for this exact model as pre-verified merely because deployment succeeds.

#### Nemotron admission gate

Nemotron outputs may not enter calibration until:

```text
[ ] exact Hugging Face repository revision is recorded
[ ] model loads/deploys in the chosen inference environment
[ ] inference-engine name/version are recorded when exposed
[ ] chat endpoint used by TRACE-Well is confirmed
[ ] tokenizer/server-resolved chat template is inspected or otherwise evidenced
[ ] intended Nemotron role markers or equivalent rendered prompt are confirmed
[ ] chat_template_digest is recorded
[ ] rendered_prompt_digest is recorded for the effective judged request
[ ] one raw request/response pair is manually inspected for coherent instruction following
[ ] plain-completion fallback is excluded
[ ] decoding_determinism_class is initially recorded as unknown
```

A plausible-looking answer is insufficient while effective prompt rendering remains unknown.

A managed endpoint that cannot expose enough evidence for the template/rendered-prompt gate remains `transport_only` and cannot contribute calibration records.

## Deferred domain-specialization extension

### MedGemma 1.5 4B — not part of the initial 24-item study

**Official repository:** `google/medgemma-1.5-4b-it`

MedGemma is deferred because the initial corpus is text-only and domain-agnostic, while MedGemma's healthcare/multimodal specialization is a distinct experimental axis.

If a healthcare-domain extension is opened:

- pin the exact repository revision actually deployed/downloaded;
- re-check model card and terms at execution time;
- validate serving stack and effective chat template;
- record both template and rendered-prompt digests;
- freeze a healthcare-specific corpus before inspecting model outputs;
- describe text-only results only as evaluation of the model's **text-reasoning slice**;
- do not generalize text-only findings to multimodal or imaging performance.

No static weight-size figures are frozen unless verified from the exact artifact used.

## Model identifier and revision rule

Only model identifiers resolvable to a current, inspectable upstream model card may appear in the experiment matrix.

At execution time, a model name alone is insufficient provenance. Each real-model run records the exact immutable upstream revision corresponding to the weights/tokenizer/config actually used or deployed.

For managed endpoints, endpoint deployment metadata is the primary source for the deployed model revision.

## Serving boundary

TRACE-Well now has two explicit adapter surfaces:

```text
scripts/local_openai_compatible_judge.py
scripts/hf_endpoint_judge.py
```

The local adapter remains loopback-only.

The Hugging Face endpoint adapter accepts an HTTPS dedicated endpoint and requires the canonical model id plus immutable model revision to be supplied explicitly.

A serving engine is an implementation detail, not evidence that the model was prompted correctly.

Every authority-relevant real-model execution records:

```text
model
model_revision
weights_digest, when available
inference_engine
inference_engine_version
quantization
decoding_determinism_class
seed
generation_parameters
judge_prompt_version
rubric_version
chat_template_digest
rendered_prompt_digest
```

`chat_template_digest` identifies the template source/effective template configuration. `rendered_prompt_digest` identifies the exact effective rendered prompt for the judged request. They answer different reproducibility questions and both are required for authority-relevant calibration records.

Do not infer decoding determinism from `temperature=0` alone.

## Serving-engine provenance policy

The initial study does not treat OpenAI-compatible serving paths as interchangeable evidence sources.

| Path | Artifact path | Primary format | Initial TRACE-Well role |
|---|---|---|---|
| HF Inference Endpoint | managed deployment from Hub | engine-dependent | preferred no-self-host Tier-0 transport path; calibration only if full provenance can be demonstrated |
| `transformers serve` | native Hugging Face repo/model loading | safetensors | valid local reference/cross-check path |
| TGI | native Hugging Face loading | safetensors | valid alternate; not required initially |
| vLLM | native Hugging Face loading where supported | safetensors | primary local Tier-0/Tier-1 path unless model-specific admission fails |
| `llama.cpp` | direct Hugging Face GGUF repo/file via `-hf` | GGUF | independent artifact/engine cross-check when specifically needed |
| Ollama | HF GGUF ingestion into Ollama-managed manifests/blobs | GGUF, re-wrapped | exploratory unless served artifact provenance is reconciled |
| SGLang | native or Transformers-backed HF loading | safetensors primarily | later alternate; not required initially |

Engine proliferation is not a goal. Add a second serving path only to answer a specific provenance, compatibility, or reproducibility question.

Cross-engine disagreement is first classified as an execution/template/artifact difference before it is interpreted as semantic-model instability.

## Transport preflight

### Tier-0 Qwen — hosted Path A

1. Create a dedicated HF Inference Endpoint for `Qwen/Qwen2.5-0.5B-Instruct`.
2. Record exact deployed model revision from endpoint metadata.
3. Record selected serving engine/version when exposed.
4. Send one direct raw chat-completions request outside TRACE-Well.
5. Confirm a coherent assistant response.
6. Send the same semantic request through `scripts/hf_endpoint_judge.py`.
7. Confirm a valid `JudgeResponse` with model id, immutable revision, and known engine provenance.
8. Run one existing semantic fixture end-to-end.
9. Repeat the same request at least 3 times.
10. Explicitly document any unavailable template/rendered-prompt/artifact provenance.

Hosted Path A completes Tier-0 transport even if some calibration-grade provenance is unavailable, but evidence remains `transport_only` in that case.

### Tier-0 Qwen — local Path B

1. Start the selected documented local OpenAI-compatible server.
2. Record exact model revision and serving-engine version.
3. Identify and hash the effective chat template.
4. Send one direct raw chat-completions request outside TRACE-Well.
5. Capture/hash the effective rendered prompt.
6. Confirm a coherent assistant response.
7. Send the same semantic request through `local_openai_compatible_judge.py`.
8. Confirm a valid `JudgeResponse` with complete provenance.
9. Run one existing semantic fixture end-to-end and confirm `semantic_result.json` persistence.
10. Repeat the same request at least 3 times before classifying decoding behavior.

Only after Tier 0 succeeds should Tier 1 begin.

### Tier-1 Nemotron preflight

1. Record exact model revision and inference-engine version when available.
2. Inspect/evidence the tokenizer/server-resolved chat template.
3. Confirm intended Nemotron role markers or equivalent rendered prompt.
4. Record `chat_template_digest`.
5. Send one raw chat-completions request.
6. Record `rendered_prompt_digest` for the effective request.
7. Inspect the response manually for coherent instruction following.
8. Retain rendered-template/server-log evidence when available.
9. Document any deviation from the model-card-recommended format.

If a managed endpoint cannot satisfy steps 2–6, it remains a transport path rather than a calibration path.

## Blinding

Each item receives an opaque `item_id`.

Judge package must not contain human label, expected calibration label, human rationale, or adjudicator identity.

Human package must not contain judge candidate label, judge rationale, model-generated confidence, fixture expected label, or model identity where avoidable.

Judge and human records are joined only after both sides are complete.

## Human labels

Allowed reference labels:

```text
PASS
FAIL
REVIEW
```

Human/domain-expert labels are calibration reference evidence, not automatic runtime authority. If multiple raters are used, retain individual labels before deriving any adjudicated label.

## Repetition policy

For each admitted model/configuration:

- run each calibration item at least 3 times in the first repeatability pass;
- hold model revision, engine version, template, prompt/rubric versions, and generation configuration fixed within a repetition block;
- persist both prompt digests for every authority-relevant run;
- persist every raw candidate label and provenance record before aggregation.

If a configuration is initially `unknown`, repetition evidence may justify a new determinism classification only for future runs; prior provenance records are not rewritten.

## Primary descriptive outputs

The first report is descriptive only. Record:

- exact judge/human label agreement;
- complete PASS / FAIL / REVIEW confusion counts;
- PASS↔FAIL disagreements;
- PASS/FAIL↔REVIEW disagreements;
- repeated-run label instability;
- missing/invalid judge responses;
- evidence-reference quality issues;
- prompt/template, engine, or artifact mismatches;
- qualitative disagreement categories.

Do not claim statistical generalization from the initial corpus.

## Disagreement taxonomy

At minimum:

```text
unsupported inference
missed uncertainty
excessive abstention
insufficient abstention
rubric ambiguity
evidence-selection error
prompt/template integration error
serving-engine integration error
artifact/quantization mismatch
output-format/protocol error
repeat instability
human-rater disagreement
other
```

Integration/artifact errors are separate from semantic-model errors.

## ADR-0015 decision gate

[`ADR-0015`](adr/0015-semantic-fail-propagation-vs-review.md) remains **Proposed** throughout the initial study.

The initial 24-item Stage-B study **cannot authorize semantic-only FAIL**, regardless of observed agreement.

Its authority-relevant outcome is limited to:

```text
STOP
REFINE
ADVANCE to a separately preregistered validation phase
```

Necessary conditions even to reach `ADVANCE` include:

```text
[ ] Tier-0 transport control completed
[ ] Tier-1 candidate passed prompt-template admission
[ ] chat_template_digest and rendered_prompt_digest captured for authority-relevant runs
[ ] blinded human labels completed
[ ] calibration report generated from exact joined records
[ ] repeated-run stability characterized
[ ] disagreement taxonomy reviewed
[ ] known integration/template errors excluded or documented
[ ] immutable model revision and full judge provenance recorded
```

A hosted endpoint that remains `transport_only` cannot satisfy the authority-relevant prompt-provenance gate.

Any future Stage-C quantitative threshold must be preregistered before Stage-C outcomes are inspected.

Until ADR-0015 is explicitly resolved:

```text
semantic candidate FAIL -> integrated REVIEW
semantic-only SafetyFinding -> prohibited
```

## Claims boundary

This plan supports **prototype evaluation-engineering evidence** only. It does not establish clinical validity, clinical efficacy, patient safety, comprehensive model safety, statistically generalizable judge performance, regulatory compliance, production readiness, or semantic-only release authority.
