# TRACE-Well V1.6 — Semantic-Judge Scope

## Branch and freeze boundary

V1.6 semantic-judge work is developed on `semantic-judge-v1.6`.

The V1.5 freeze point is commit:

```text
791c92c3da43e33a2e986e63f2f7ef9f845ac70b
```

A convenience branch, `freeze/v1.5.0-pending-po9`, points to that commit. The commit SHA is the immutable evidence anchor; the branch name is only a human-readable reference.

V1.5 remains **Done** with blind independent-human PO-9 signoff pending. V1.6 work must not be used to retroactively expand V1.5 claims.

## Objective

V1.6 extends the deterministic evaluation kernel with an **isolated semantic-judge capability** for constructs that cannot be resolved mechanically from observable trace evidence alone.

The semantic judge is an evaluation component, not ground truth.

## V1.6 first milestone

The first milestone proves the judge interface before integrating any real model/provider.

It includes:

1. a strict `JudgeRequest` / `JudgeResponse` JSON protocol;
2. out-of-process execution through a subprocess boundary;
3. a deterministic mock semantic judge;
4. timeout, non-zero-exit, malformed-output, and schema-validation handling;
5. explicit judge provenance;
6. explicit **decoding determinism class**;
7. conservative integration with existing verdict semantics;
8. tests proving deterministic failures and global specification inconsistency retain their existing precedence;
9. an end-to-end semantic fixture path that persists `semantic_result.json` separately from V1.5 deterministic evidence;
10. an explicit milestone-1 rule that semantic-only output cannot create or close a `SafetyFinding`.

## Explicit non-goals for the first milestone

The first milestone does **not** include:

- hosted-provider integration;
- local model inference dependencies in the base runtime;
- semantic-only FAIL authority;
- semantic-only `SafetyFinding` creation or closure;
- confidence-score thresholds;
- multi-judge voting;
- statistical reliability claims;
- calibration claims against human labels;
- clinical validity, efficacy, or safety claims;
- production release-governance use.

## Observable-evidence boundary

Semantic judge requests are constructed only from an explicit allowlist of observable trace fields:

```text
event_id
event_type
actor
input
output
tool
tool_arguments
tool_result
authorization_state
evidence_refs
```

`TraceEvent.metadata` is intentionally excluded. Fixture markers, hidden controls, internal annotations, and future non-observable scaffolding must not leak into semantic-judge input.

## Verdict precedence

V1.6 preserves the existing deterministic precedence before considering semantic judgment:

```text
1. global specification inconsistency -> REVIEW
2. established deterministic obligation failure -> FAIL
3. unresolved required deterministic construct -> REVIEW
4. semantic-judge result may be considered only if 1-3 do not already determine the outcome
```

Therefore:

- a semantic judge cannot erase a deterministic `FAIL`;
- **global specification inconsistency still outranks deterministic `FAIL`** because the specification is not reliable enough to support behavioral adjudication;
- semantic uncertainty remains `REVIEW`;
- whether a semantic-only violation may become final `FAIL` remains unresolved under ADR-0015.

## Semantic-only FAIL authority

ADR-0015 remains **Proposed**.

For the first milestone, a semantic judge may produce a structured candidate judgment, but the project does not yet grant semantic-only judgment final FAIL authority. That decision requires calibration evidence and an explicit ADR-0015 resolution.

## Finding authority

Milestone-1 `SafetyFinding` authority remains **deterministic-only**.

A `SafetyFinding` may be created only from the frozen V1.5 deterministic pair result. Semantic output is persisted separately as `semantic_result.json` and cannot create, close, or mutate a `SafetyFinding`.

Required examples:

```text
deterministic PASS + semantic candidate PASS   -> integrated PASS   -> no finding
deterministic PASS + semantic candidate FAIL   -> integrated REVIEW -> no finding
deterministic PASS + semantic candidate REVIEW -> integrated REVIEW -> no finding
deterministic FAIL + semantic candidate PASS   -> integrated FAIL   -> deterministic finding remains
```

If a future implementation grants semantic-only FAIL or finding authority, ADR-0015 must first be resolved and the finding lifecycle must be updated explicitly. It must not emerge accidentally from integration code.

## Judge provenance

Every semantic-judge execution must persist enough information to answer both:

1. **what judge ran?**
2. **was this output expected to reproduce exactly?**

Required provenance fields for the first milestone:

```text
judge_id
judge_version
execution_mode
model
model_revision
weights_digest
inference_engine
inference_engine_version
quantization
decoding_determinism_class
seed
generation_parameters
judge_prompt_version
rubric_version
```

Fields that do not apply must be explicitly null rather than silently omitted where the schema requires them.

### Decoding determinism class

`decoding_determinism_class` is a first-class categorical field, not an inferred property of `generation_parameters`.

Initial values:

```text
deterministic
seeded_stochastic
unseeded_stochastic
unknown
```

This classification is provenance. It does not by itself determine correctness or trustworthiness.

## Human calibration boundary

A real semantic judge must eventually be evaluated against blinded human/domain-expert labels. Judge self-consistency or agreement with another LLM is not sufficient evidence of semantic correctness.

Calibration, disagreement handling, and any semantic-only FAIL policy belong to later V1.6 milestones after the protocol is stable.

## Claims boundary

Until calibration evidence exists, V1.6 semantic-judge outputs are **prototype evaluation-engineering evidence** only.

Do not describe semantic-judge outputs as clinical ground truth, validated expert judgment, comprehensive safety evidence, or release authorization.
