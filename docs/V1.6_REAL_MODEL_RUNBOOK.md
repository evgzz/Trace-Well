# TRACE-Well V1.6 — Real-Model Execution Runbook

## Purpose

Execute the first real semantic-judge transport proof reproducibly, beginning with the Tier-0 control model from `docs/V1.6_EVALUATION_PLAN.md`.

This runbook is procedural. It does not claim that any real model has been executed merely because the repository contains these commands.

## Current Tier-0 target

```text
Qwen/Qwen2.5-0.5B-Instruct
```

Tier-0 proves transport, prompt application, adapter behavior, provenance capture, and repeatability plumbing. It does **not** establish semantic-judge validity.

## Preconditions

Before starting:

```text
[ ] checkout semantic-judge-v1.6
[ ] repository CI is green
[ ] Python >= 3.11
[ ] TRACE-Well base environment installed
[ ] separate local inference environment available
[ ] sufficient local compute for selected model/server
[ ] exact serving-engine version known
[ ] outbound model download permitted if not already cached
```

Do not add model-serving dependencies to the TRACE-Well base runtime merely to execute this runbook.

## Run directory

Create a dedicated local evidence directory that is not silently mixed with V1.5 evidence:

```bash
export RUN_ID=tier0-qwen-001
mkdir -p results/real-model/$RUN_ID
```

Recommended files:

```text
results/real-model/$RUN_ID/
  chat_template.txt
  rendered_prompt.txt
  raw_request.json
  raw_response.json
  adapter_request.json
  adapter_response.json
  semantic_result.json
  manifest.json
  notes.txt
```

## Step 1 — pin the model revision

Resolve the exact immutable Hugging Face revision corresponding to the model/tokenizer/config actually loaded.

Record:

```text
model_id = Qwen/Qwen2.5-0.5B-Instruct
hf_revision = <immutable revision>
```

Do not record only `main`, `latest`, or a mutable branch/tag.

If the serving stack downloads from the Hub automatically, capture the resolved revision from the local HF cache metadata or serving logs before accepting the run into the evidence record.

## Step 2 — start one primary local server

Use one safetensors-side OpenAI-compatible engine selected by the evaluation plan.

Example shape for vLLM:

```bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --host 127.0.0.1 \
  --port 8000
```

Record the exact serving-engine version separately.

If using another admitted engine such as Transformers Serve, record that engine/version instead. Do not claim cross-engine equivalence.

## Step 3 — capture the effective chat template

Capture the exact chat-template source string used by the tokenizer/serving stack into:

```text
results/real-model/$RUN_ID/chat_template.txt
```

This file is evidence-bearing.

Do not substitute a human-written approximation of the template.

## Step 4 — capture one rendered prompt

Use the same system/user content that will be sent through the TRACE-Well judge adapter and capture the fully rendered prompt after chat-template application into:

```text
results/real-model/$RUN_ID/rendered_prompt.txt
```

The rendered prompt must correspond to the actual request under test.

If the serving engine does not expose rendered prompt text directly, use the tokenizer for the exact pinned model revision to render the same message structure and document that method in `notes.txt`.

## Step 5 — direct raw chat request

Before involving TRACE-Well, send one raw request directly to the local server.

Example:

```bash
curl -sS http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d @results/real-model/$RUN_ID/raw_request.json \
  > results/real-model/$RUN_ID/raw_response.json
```

Acceptance check:

```text
[ ] HTTP request succeeded
[ ] response is valid JSON
[ ] assistant content is coherent
[ ] response corresponds to the expected chat endpoint
[ ] no accidental plain-completion fallback is observed
```

Transport success is not semantic calibration.

## Step 6 — TRACE-Well adapter request

Prepare one `JudgeRequest` JSON in:

```text
results/real-model/$RUN_ID/adapter_request.json
```

Run the existing adapter:

```bash
python scripts/local_openai_compatible_judge.py \
  --endpoint http://127.0.0.1:8000/v1/chat/completions \
  --model Qwen/Qwen2.5-0.5B-Instruct \
  --model-revision <IMMUTABLE_HF_REVISION> \
  --inference-engine vllm \
  --inference-engine-version <VERSION> \
  --decoding-determinism-class unknown \
  --temperature 0 \
  --max-tokens 256 \
  --judge-prompt-version local-openai-compatible-v1 \
  --rubric-version semantic-rubric-v1 \
  --chat-template-digest <SHA256_FROM_CHAT_TEMPLATE> \
  --rendered-prompt-digest <SHA256_FROM_RENDERED_PROMPT> \
  < results/real-model/$RUN_ID/adapter_request.json \
  > results/real-model/$RUN_ID/adapter_response.json
```

Acceptance check:

```text
[ ] output validates as JudgeResponse
[ ] request_id matches
[ ] model + immutable revision recorded
[ ] engine + version recorded
[ ] chat_template_digest recorded
[ ] rendered_prompt_digest recorded
[ ] decoding_determinism_class remains unknown for the first run
```

## Step 7 — run one semantic fixture end-to-end

Run one existing semantic fixture through `tracewell.semantic_pipeline.run_semantic_fixture` or an equivalent repository-owned invocation using the same adapter command and configuration.

The resulting run directory must include:

```text
canonical_trace.json
perturbed_trace.json
result.json
manifest.json
semantic_result.json
```

For a deterministic PASS pair plus semantic candidate FAIL/REVIEW, no semantic-only `finding.json` may appear.

## Step 8 — record the real-model manifest

Use the repository recorder:

```bash
python scripts/record_model_run.py \
  --run-id $RUN_ID \
  --model-id Qwen/Qwen2.5-0.5B-Instruct \
  --hf-revision <IMMUTABLE_HF_REVISION> \
  --artifact-format safetensors \
  --artifact-reference Qwen/Qwen2.5-0.5B-Instruct@<IMMUTABLE_HF_REVISION> \
  --serving-engine vllm \
  --serving-engine-version <VERSION> \
  --endpoint http://127.0.0.1:8000/v1/chat/completions \
  --decoding-determinism-class unknown \
  --generation-parameters '{"temperature":0.0,"max_tokens":256}' \
  --judge-prompt-version local-openai-compatible-v1 \
  --rubric-version semantic-rubric-v1 \
  --chat-template results/real-model/$RUN_ID/chat_template.txt \
  --rendered-prompt results/real-model/$RUN_ID/rendered_prompt.txt \
  --request results/real-model/$RUN_ID/adapter_request.json \
  --response results/real-model/$RUN_ID/adapter_response.json \
  --output results/real-model/$RUN_ID/manifest.json
```

If an exact local weights file is available and hashing it is practical, also pass:

```bash
--weights-file <PATH_TO_EXACT_WEIGHT_ARTIFACT>
```

For multi-file safetensors checkpoints, do not invent a single weights digest. Record `weights_digest: null` unless a canonical aggregate-digest procedure has been defined and applied consistently.

## Step 9 — repeatability block

Repeat the exact same semantic request at least three times while holding fixed:

```text
model revision
serving-engine version
chat-template digest
rendered-prompt digest
judge prompt version
rubric version
generation parameters
seed, if applicable
```

Persist each response separately before aggregation.

Do not rewrite the first run's `decoding_determinism_class`. It remains the provenance classification assigned at that run. A later assessment may classify future runs differently.

## Step 10 — Tier-0 exit record

Tier 0 is complete only when all are true:

```text
[ ] immutable HF revision captured
[ ] raw direct chat request succeeded
[ ] effective chat template captured
[ ] rendered prompt captured
[ ] both prompt digests recorded
[ ] TRACE-Well adapter produced valid JudgeResponse
[ ] one semantic fixture completed end-to-end
[ ] real-model manifest written successfully
[ ] at least 3 identical-configuration repetitions persisted
[ ] any instability documented
```

Tier-0 completion means only:

> The real-model transport and provenance path was exercised successfully under the recorded configuration.

It does not mean the model is calibrated or suitable for semantic-only FAIL authority.

## Step 11 — do not advance prematurely

Do not start the blinded 24-item calibration corpus until Tier 0 is complete.

Do not start Nemotron calibration until the separate Nemotron prompt-template admission gate in `docs/V1.6_EVALUATION_PLAN.md` is complete.

Do not resolve ADR-0015 from Tier-0 evidence.

## Optional second-engine cross-check

After Tier 0 is complete, the evaluation plan may use a second serving engine to answer a specific reproducibility question.

The preferred initial cross-check should keep the upstream model/revision as comparable as practical. If artifact format or quantization changes, treat that as an additional changed variable and record it explicitly.

Cross-engine disagreement is first classified as serving/template/artifact difference, not immediately as semantic-model instability.

## Claims boundary

This runbook produces **prototype evaluation-engineering evidence** only.

No run under this procedure establishes clinical validity, patient safety, comprehensive model safety, statistically generalizable judge performance, production readiness, or semantic-only release authority.
