# TRACE-Well V1.6 — Real-Model Execution Runbook

## Purpose

Execute the first real semantic-judge transport proof reproducibly, beginning with the Tier-0 control model from `docs/V1.6_EVALUATION_PLAN.md`.

This runbook is procedural. It does not claim that any real model has been executed merely because the repository contains these commands.

## Current Tier-0 target

```text
Qwen/Qwen2.5-0.5B-Instruct
```

Tier-0 proves transport, prompt application where observable, adapter behavior, provenance capture, and repeatability plumbing. It does **not** establish semantic-judge validity.

## Two supported Tier-0 execution paths

### Path A — dedicated Hugging Face Inference Endpoint (preferred no-self-host option)

Use a dedicated Hugging Face Inference Endpoint when you want the exact Hub model without managing a local GPU/server.

Advantages:

- exact Hub repository can be selected;
- endpoint deployment metadata records a specific model revision;
- serving engine can be selected/configured by the endpoint deployment;
- OpenAI Chat Completions is available on compatible endpoint engines;
- no local model download or GPU process is required.

Limitations:

- exact weights digest may not be directly exposed;
- exact rendered prompt may not be exposed by the managed serving layer;
- chat-template source can be derived from the pinned tokenizer revision, but TRACE-Well must distinguish derived template evidence from server-observed rendered-prompt evidence;
- hosted endpoint output is **not calibration-grade by default** unless the deployment exposes enough information to satisfy the frozen provenance requirements.

### Path B — local/self-hosted OpenAI-compatible server

Use vLLM, Transformers Serve, or another admitted local server when you need maximum prompt/artifact/runtime provenance.

This path can satisfy the full calibration-grade manifest when exact template/rendered-prompt/runtime evidence is captured.

## Evidence classes

TRACE-Well distinguishes:

```text
transport_only
calibration_candidate
```

A hosted dedicated-endpoint run may establish `transport_only` evidence even when some template/artifact provenance is unavailable.

A run may enter `calibration_candidate` evidence only when all provenance required by `experiments/v1.6/manifest.schema.json` is available and materially corresponds to the actual serving configuration.

Do not fill unavailable hosted provenance with guessed values.

## Run directory

Create a dedicated local evidence directory that is not silently mixed with V1.5 evidence:

```bash
export RUN_ID=tier0-qwen-001
mkdir -p results/real-model/$RUN_ID
```

Recommended files:

```text
results/real-model/$RUN_ID/
  chat_template.txt
  rendered_prompt.txt
  raw_request.json
  raw_response.json
  adapter_request.json
  adapter_response.json
  semantic_result.json
  manifest.json
  notes.txt
```

For hosted `transport_only` runs, files that cannot be obtained from the actual endpoint must be omitted rather than fabricated. Record the limitation in `notes.txt`.

## Step 1 — pin the model revision

Resolve the exact immutable Hugging Face revision corresponding to the model/tokenizer/config actually loaded or deployed.

Record:

```text
model_id = Qwen/Qwen2.5-0.5B-Instruct
hf_revision = <immutable revision>
```

Do not record only `main`, `latest`, or a mutable branch/tag.

For Path A, use the dedicated endpoint deployment metadata/model revision.

For Path B, capture the resolved revision from local HF cache metadata or serving logs before accepting the run into the evidence record.

## Step 2A — create/use a dedicated HF Inference Endpoint

Create a dedicated endpoint for the exact Tier-0 model and pin the revision in the deployment configuration when supported.

Record at minimum:

```text
endpoint URL
model repository
immutable model revision
selected serving engine
serving-engine version, when exposed
instance hardware/configuration, when exposed
```

The endpoint must expose an OpenAI-compatible chat-completions API for this runbook path.

## Step 2B — start one primary local server

Use one safetensors-side OpenAI-compatible engine selected by the evaluation plan.

Example shape for vLLM:

```bash
vllm serve Qwen/Qwen2.5-0.5B-Instruct \
  --host 127.0.0.1 \
  --port 8000
```

Record the exact serving-engine version separately.

If using another admitted engine such as Transformers Serve, record that engine/version instead. Do not claim cross-engine equivalence.

## Step 3 — capture the effective chat template when available

For either path, derive the exact chat-template source string from the tokenizer belonging to the same pinned model revision when possible.

Store it in:

```text
results/real-model/$RUN_ID/chat_template.txt
```

This proves the model-revision template source, but for a managed endpoint it does **not by itself prove** that the server applied that exact template.

For calibration-candidate evidence, the endpoint/server must provide enough information to show that the deployed serving stack actually used the recorded template or an equivalent rendered prompt.

## Step 4 — capture one rendered prompt when available

Use the same system/user content that will be sent through the TRACE-Well judge adapter and capture the fully rendered prompt after chat-template application into:

```text
results/real-model/$RUN_ID/rendered_prompt.txt
```

For Path B, use the exact serving tokenizer/template and document the capture method.

For Path A, use server/endpoint observability if available. If the managed endpoint does not expose the rendered prompt, do not synthesize it and call it observed evidence. A locally rendered prompt may be retained as **derived comparison evidence**, but the run remains `transport_only` unless equivalence to the endpoint's effective prompt can be demonstrated.

## Step 5A — direct raw request to dedicated HF endpoint

Example shape:

```bash
curl -sS "$HF_ENDPOINT_URL/v1/chat/completions" \
  -H "Authorization: Bearer $HF_TOKEN" \
  -H 'Content-Type: application/json' \
  -d @results/real-model/$RUN_ID/raw_request.json \
  > results/real-model/$RUN_ID/raw_response.json
```

Acceptance check:

```text
[ ] HTTPS request succeeded
[ ] response is valid JSON
[ ] assistant content is coherent
[ ] response corresponds to chat-completions path
[ ] deployed model revision is recorded independently from the response payload
```

## Step 5B — direct raw request to local server

```bash
curl -sS http://127.0.0.1:8000/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d @results/real-model/$RUN_ID/raw_request.json \
  > results/real-model/$RUN_ID/raw_response.json
```

Acceptance check:

```text
[ ] HTTP request succeeded
[ ] response is valid JSON
[ ] assistant content is coherent
[ ] response corresponds to the expected chat endpoint
[ ] no accidental plain-completion fallback is observed
```

Transport success is not semantic calibration.

## Step 6A — TRACE-Well dedicated endpoint adapter

Prepare one `JudgeRequest` JSON in:

```text
results/real-model/$RUN_ID/adapter_request.json
```

Run:

```bash
python scripts/hf_endpoint_judge.py \
  --base-url "$HF_ENDPOINT_URL" \
  --api-model <ENDPOINT_API_MODEL_NAME> \
  --model Qwen/Qwen2.5-0.5B-Instruct \
  --model-revision <IMMUTABLE_HF_REVISION> \
  --inference-engine <ENDPOINT_ENGINE> \
  --inference-engine-version <VERSION_IF_KNOWN> \
  --decoding-determinism-class unknown \
  --temperature 0 \
  --max-tokens 256 \
  --judge-prompt-version hf-endpoint-v1 \
  --rubric-version semantic-rubric-v1 \
  < results/real-model/$RUN_ID/adapter_request.json \
  > results/real-model/$RUN_ID/adapter_response.json
```

If the actual deployed chat template/rendered prompt can be verified, additionally pass:

```bash
--chat-template-digest <SHA256> \
--rendered-prompt-digest <SHA256>
```

Do not provide these fields merely from local assumptions when they cannot be tied to the managed endpoint's actual execution.

## Step 7 — run one semantic fixture end-to-end

Run one existing semantic fixture through `tracewell.semantic_pipeline.run_semantic_fixture` or an equivalent repository-owned invocation using the selected adapter command and configuration.

The resulting run directory should include:

```text
canonical_trace.json
perturbed_trace.json
result.json
manifest.json
semantic_result.json
```

For a deterministic PASS pair plus semantic candidate FAIL/REVIEW, no semantic-only `finding.json` may appear.

## Step 8A — hosted transport-only record

When a dedicated endpoint does not expose enough prompt/artifact provenance for `experiments/v1.6/manifest.schema.json`, do **not** force it into that calibration-grade schema.

Instead record in `notes.txt`:

```text
evidence_class = transport_only
model_id
hf_revision
endpoint URL
serving engine / version when known
raw request digest
raw response digest
adapter request digest
adapter response digest
known missing provenance fields
```

A future repository-owned hosted-transport schema may formalize this record. Until then, the evidence class must remain explicit.

## Step 8B — calibration-candidate manifest

Use `scripts/record_model_run.py` only when the evidence actually satisfies the frozen real-model manifest requirements.

Example for local/self-hosted execution:

```bash
python scripts/record_model_run.py \
  --run-id $RUN_ID \
  --model-id Qwen/Qwen2.5-0.5B-Instruct \
  --hf-revision <IMMUTABLE_HF_REVISION> \
  --artifact-format safetensors \
  --artifact-reference Qwen/Qwen2.5-0.5B-Instruct@<IMMUTABLE_HF_REVISION> \
  --serving-engine vllm \
  --serving-engine-version <VERSION> \
  --endpoint http://127.0.0.1:8000/v1/chat/completions \
  --decoding-determinism-class unknown \
  --generation-parameters '{"temperature":0.0,"max_tokens":256}' \
  --judge-prompt-version local-openai-compatible-v1 \
  --rubric-version semantic-rubric-v1 \
  --chat-template results/real-model/$RUN_ID/chat_template.txt \
  --rendered-prompt results/real-model/$RUN_ID/rendered_prompt.txt \
  --request results/real-model/$RUN_ID/adapter_request.json \
  --response results/real-model/$RUN_ID/adapter_response.json \
  --output results/real-model/$RUN_ID/manifest.json
```

For multi-file safetensors checkpoints, do not invent a single weights digest. Record `weights_digest: null` unless a canonical aggregate-digest procedure has been defined and applied consistently.

## Step 9 — repeatability block

Repeat the exact same semantic request at least three times while holding fixed all known configuration values.

For hosted Path A, also verify that the endpoint deployment/revision did not change between repetitions.

Persist each response separately before aggregation.

Do not upgrade `decoding_determinism_class` from `unknown` merely because three outputs happen to match.

## Step 10 — Tier-0 exit record

### Hosted Path A exit

Hosted Tier 0 transport is complete when:

```text
[ ] exact endpoint deployment + immutable model revision recorded
[ ] direct chat request succeeded
[ ] TRACE-Well dedicated endpoint adapter produced valid JudgeResponse
[ ] one semantic fixture completed end-to-end
[ ] at least 3 identical-configuration repetitions persisted
[ ] known provenance gaps explicitly documented
[ ] evidence_class remains transport_only unless calibration-grade provenance was actually demonstrated
```

### Local Path B exit

Local Tier 0 is complete only when all are true:

```text
[ ] immutable HF revision captured
[ ] raw direct chat request succeeded
[ ] effective chat template captured
[ ] rendered prompt captured
[ ] both prompt digests recorded
[ ] TRACE-Well adapter produced valid JudgeResponse
[ ] one semantic fixture completed end-to-end
[ ] real-model manifest written successfully
[ ] at least 3 identical-configuration repetitions persisted
[ ] any instability documented
```

Tier-0 completion means only:

> The real-model transport and provenance path was exercised successfully under the recorded configuration.

It does not mean the model is calibrated or suitable for semantic-only FAIL authority.

## Step 11 — do not advance prematurely

Do not start the blinded 24-item calibration corpus until Tier 0 is complete.

Do not start Nemotron calibration until the separate Nemotron prompt-template admission gate in `docs/V1.6_EVALUATION_PLAN.md` is complete.

Do not resolve ADR-0015 from Tier-0 evidence.

## Nemotron and dedicated endpoints

A dedicated HF endpoint is a plausible Tier-1 deployment path for `nvidia/Nemotron-Mini-4B-Instruct`, but deployability and prompt-template correctness must be verified at endpoint creation time.

Because Nemotron has a model-specific prompt template, a managed endpoint is not admitted to calibration merely because deployment succeeds. The endpoint must still satisfy the Nemotron admission gate from `docs/V1.6_EVALUATION_PLAN.md`.

## Claims boundary

This runbook produces **prototype evaluation-engineering evidence** only.

No run under this procedure establishes clinical validity, patient safety, comprehensive model safety, statistically generalizable judge performance, production readiness, or semantic-only release authority.
